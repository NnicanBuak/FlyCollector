## 1) Базовые принципы

* Один публичный тип на файл. Имя файла = имя типа.
* Public API — максимально минимальный. Внешним контрагентам показываем только то, что нужно.
* Строго включаем **C# 8+ Nullable Reference Types** в проекте; JetBrains Annotations не требуются.
* Стабильные имена и контракты — важнее «супер‑умных» сокращений. Переименования сопровождаем миграцией данных.

## 2) Нейминг и стиль C#

* **Классы/структуры/enum/интерфейсы/события**: `PascalCase` (интерфейсы с префиксом `I`).
* **Поля**: приватные — `camelCase` с префиксом `_` (например, `_speed`), защищённые — `camelCase`, публичные — свойства.
* **Свойства/методы**: `PascalCase`.
* **Параметры/локальные**: `camelCase`.
* **Булевы**: `is/has/can/should` (`IsAlive`, `HasEnergy`).
* **Обработчики событий**: `OnSomethingHappened`.
* **Константы**: `PascalCase` (например, `DefaultSpeed`).
* **Async‑методы**: постфикс `Async`.

## 3) Форматирование и .editorconfig

* Отступы — 4 **пробела**. Конец строки — `LF`. Кодировка — `utf-8`.
* Максимальная длина строки — ориентир 120–140 символов.
* Скобки — K&R/Allman на усмотрение команды; по умолчанию — **Allman** для C#.

```ini
# .editorconfig (фрагмент)
root = true

[*.cs]
indent_style = space
indent_size = 4
end_of_line = lf
charset = utf-8
insert_final_newline = true
max_line_length = 140
csharp_new_line_before_open_brace = all
csharp_preserve_single_line_statements = false
csharp_preserve_single_line_blocks = false

# nullable включайте в .csproj: <Nullable>enable</Nullable>
```

## 4) Rider‑friendly (опционально, «включено если есть Rider»)

* **Namespace Provider**: включить автогенерацию namespace по структуре папок.

  * Если верхнеуровневые папки типа `Scripts`/`Code` чисто организационные, исключить их из namespace‑корня.
* Включить **Reformat on Save** и **Optimize Imports on Save**.
* Настроить инспекции под этот гайд (например, требовать свойства вместо public полей и т.п.).

## 5) Unity‑специфика

* **MonoBehaviour**:

  * Не храните тяжёлую логику в `Update()`. Предпочитайте события, корутины, таймеры.
  * Кешируйте ссылки (компоненты, трансформы). Используйте `TryGetComponent`.
  * Не используйте `FindObjectOfType/Find` в рантайме; разрешается в Editor/отладке.
  * Ссылки задаём через `[SerializeField] private` + `nameof` в атрибутах/логах.
* **Скриптовые ссылки в инспекторе**: избегайте публичных полей; используйте `[SerializeField] private`.
* **ScriptableObject**: применяйте для конфигов/статических данных. При переименовании полей используйте `[FormerlySerializedAs]`.
* **Animator**: имена событий — факт в прошедшем времени (`HitFinished`). Подписчики — метод `AnimatorOnHitFinished()` или `OnHitFinished()` (на усмотрение команды). Это рекомендация, не жёсткое правило.
* **Жизненный цикл объектов**:

  * Не навязываем «самоуничтожение» изнутри. Если используется пул — жизненный цикл централизован (менеджер/пул решает `Release/Despawn`). Если объект самодостаточный — допустим `Destroy(gameObject)`/корутина.

## 6) Логирование и ошибки

* По умолчанию используем **`UnityEngine.Debug.Log*`**.
* Если в проекте есть адаптер логгера (обвязка), можно маршрутизировать через него. Никаких требований к кастомному `CoreLogger` в этой версии гайда.
* Типовые уровни: `Log` (инфо), `LogWarning` (восстановимо), `LogError` (ошибка, но игра может продолжать), **Assert/Exception** — критические, собираем трейс.

## 7) Архитектура (без привязки к DI/Zenject)

* Интерфейсы применяем для внешних контрактов и точек расширения.
* Зависимости передаём явно через конструкторы обычных классов или через ссылки в инспекторе для компонентов.
* Разделяем доменную логику и представление: **Plain C#** классы не должны зависеть от Unity API, если это возможно.

## 8) Организация проекта и assets

* Рекомендуемая структура:

  * `Assets/Code` (`Runtime`, `Editor`, `Tests`)
  * `Assets/Scenes`
  * `Assets/Prefabs`
  * `Assets/Art` (`Textures`, `Materials`, `Models`, `Animations`)
  * `Assets/Audio`
  * `Assets/ScriptableObjects`
  * `Assets/Plugins` / `ThirdParty`
* **Asmdef**: разбивайте на сборки (`Runtime`, `Editor`, тесты отдельно). Минимизируйте зависимости между asmdef.

## 9) Сериализация и данные

* Только сериализуемые типы/поля попадают в ScriptableObject/инспектор. Для коллекций — предпочитайте `List<T>`.
* Переименования полей — через `[FormerlySerializedAs]`.
* Внешние форматы: JSON — `System.Text.Json`/`Newtonsoft.Json` на выбор проекта.

## 10) Версионирование и CI

* **Version Control**: `Visible Meta Files`, `Force Text`, `.gitignore` для Unity, включить Smart Merge (UnityYAMLMerge) при необходимости.
* **Continuous Integration**: проверка сборки, форматирования (EditorConfig), линтеры (например, Rider Inspections), unit‑тесты.

## 11) Тестирование

* Unity Test Framework: разделять **EditMode** и **PlayMode**.
* В unit‑тестах избегать Unity API, если возможно; для взаимодействия — абстракции/интерфейсы, подменяемые заглушками.

## 12) Комментарии и документация

* Комментарии и XML‑документация — **на английском** по умолчанию (если команда не договорилась иначе).
* Документируйте публичный API и нестандартные решения.

## 13) Code Review — чек‑лист

* Нейминг/контракты согласованы? Публичная поверхность минимальна?
* Нет ли публичных полей, которые должны быть свойствами или `[SerializeField] private`?
* Нет тяжелых операций в `Update`/`FixedUpdate` без необходимости?
* Логи корректного уровня? Нет мусорных логов?
* Асмдефы/зависимости разумны? Нет циклических связей?
* Сериализация совместима с уже существующими данными? (переименования с `FormerlySerializedAs`)

Этот гайд **намеренно не содержит** правил, завязанных на Zenject/Extenject, UniRx/Reactive‑подход или ваш кастомный логгер. Если в конкретном проекте они используются, оформляйте отдельные модули‑приложения с правилами и подключайте их опционально.
